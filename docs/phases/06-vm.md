# Phase 6 — The stack-based virtual machine

**Goal:** execute Phase 5's bytecode: a `VM` struct with an instruction
pointer and a value stack, spinning in the classic
`for(;;) { switch(READ_BYTE()) ... }` dispatch loop. End state: the same
tinylang programs run on either back end, and you benchmark them.

**Why:** you are building a CPU in software. A real processor loops
forever doing three things — **fetch** the instruction its program
counter points at, **decode** what operation it encodes, **execute** it —
and a bytecode VM is that same loop written in C, aimed at your invented
instruction set instead of ARM's. The fetch-decode-execute loop you write
here is the same loop inside CPython's `ceval.c`, Lua's `lvm.c`, and — in
silicon — the M-series chip in your Mac. After this phase, "Python is
interpreted" stops being a vibe and becomes a mechanism you have
personally implemented. This is the single strongest talking point this
project gives you.

**Spine reading:**
- [Crafting Interpreters ch. 15, "A Virtual Machine"](https://craftinginterpreters.com/a-virtual-machine.html) — the phase's core chapter.

## Task 6.1 — VM skeleton + dispatch loop (~1.5h)

**Build:** `vm.h`/`vm.c`: the VM struct (chunk pointer, instruction pointer
`uint8_t* ip`, fixed-size `Value stack[256]` + stack-top pointer),
`push`/`pop`, and a `run()` loop handling just `OP_CONST` and `OP_RETURN`.

**The concept:** meet the two most famous registers in computing, wearing
C-variable costumes. The **instruction pointer** `ip` (real CPUs call it
the program counter) always points at the next byte to execute; "fetch"
is `*ip++` — read the byte, move forward — and a jump, later, will be
nothing but arithmetic on `ip`. The **stack pointer** marks the top of
the value stack where all work happens: `push` writes and advances, `pop`
retreats and reads. The dispatch loop ties them together:
`for(;;) { switch(*ip++) { case OP_CONST: ... case OP_RETURN: ... } }` —
fetch, decode (the `switch`), execute (the case body), forever. That
skeleton, plus the stack, is the *whole machine*; everything after this
task is just more `case` labels.

Two deliberate design details worth noticing. Making `ip` a raw pointer
into the byte array (rather than an integer index) saves an addition on
every single fetch — a measurable choice of the kind real VM authors
argue about, and your first taste of "this loop is so hot that
*everything* in it matters." And the fixed 256-slot stack must check for
overflow — a stack overflow that *corrupts* is a security bug, a stack
overflow that *reports* is a feature. `ponytail:` fixed-size stack with a
check; growable comes if a real program ever hits it.

**Read first:**
- [Crafting Interpreters ch. 15, §15.1–15.2](https://craftinginterpreters.com/a-virtual-machine.html) —
  the VM struct, the dispatch loop, the value stack.
- [Wikipedia — Stack machine](https://en.wikipedia.org/wiki/Stack_machine) —
  the architecture you're implementing, and who else uses it (JVM, Wasm,
  CPython...).
- [Fetch–decode–execute cycle explained](https://www.youtube.com/watch?v=jFDMZpkUWCw) (video) —
  the hardware version of your loop, with the real registers; watch it
  and map each piece onto your C variables.

**Done when:** asserts run a hand-built chunk and observe the constant
arrive on the stack; stack overflow is caught, not corrupted.

## Task 6.2 — Arithmetic on the stack (~1–1.5h)

**Build:** `OP_ADD/SUB/MUL/DIV/NEG`: pop two, compute, push one. Run real
compiler output for the first time: `compile("(1+2)*3")` → `run` → 9.

**The concept:** each arithmetic opcode is the same four-beat move: pop
the right operand, pop the left, compute, push the result. (Right pops
first because it was pushed last — the stack reverses order, and this is
exactly where the two classic VM bugs live. **Wrong operand order:**
popping left-then-right makes `SUB` compute backwards, and `2-1` starts
answering `-1`. **Stack underflow:** if the compiler emitted too few
pushes, `pop` reads garbage below the stack — the VM equivalent of a
buffer underrun.) When you wire compiler output to VM input and `(1+2)*3`
produces 9, notice *why* it works with no coordination code: the
post-order emission from task 5.3 is a *promise about stack layout* —
"operands will be on top when the operator arrives" — and the VM merely
cashes it.

The book's `BINARY_OP` macro is worth adopting: five opcodes differing
only in one character of C is exactly what C macros are for — your first
taste of them earning their keep rather than obfuscating.

**Why compilers need it:** the test this task ends on is the payoff of
having two back ends: a table of expressions asserting
`run(compile(src)) == eval(parse(src))` — your interpreter and your VM
checking *each other*, no hand-computed expected values needed. Real
language teams test exactly this way (a new JIT is tested against the
old interpreter). That cross-check suite is your regression net for the
rest of the project.

**Read first:**
- [Crafting Interpreters ch. 15, §15.3](https://craftinginterpreters.com/a-virtual-machine.html) —
  arithmetic and the binary-op macro trick.
- [A Python Interpreter Written in Python](https://aosabook.org/en/500L/a-python-interpreter-written-in-python.html) —
  a real (tiny) Python VM doing exactly these pops and pushes, in
  readable Python; the "A Tiny Interpreter" section is your VM with
  different variable names.
- [Wikipedia — Reverse Polish notation](https://en.wikipedia.org/wiki/Reverse_Polish_notation) —
  the "Postfix evaluation algorithm" section *is* your run loop,
  described mathematically.

**Done when:** a table-driven test asserts `run(compile(src)) == eval(parse(src))`
for a pile of expressions — your two back ends checking each other. That
cross-check is your regression suite for the rest of the project.

## Task 6.3 — Runtime errors + a trace mode (~1.5h)

**Build:** graceful runtime errors (div-by-zero, and type errors once bools
flow through), plus a `#ifdef DEBUG_TRACE` mode printing each instruction
(via the Phase 5 disassembler) and the stack contents as it executes.

**The concept:** the trace is the VM's flight recorder: before each
instruction, print the current stack, then disassemble the instruction
about to run. The output — `CONST` push, `CONST` push, `ADD` collapse —
is a movie of the machine thinking, and watching `1+2*3` scroll by is the
moment stack machines go from understood-in-theory to *obvious*. The C
idiom carrying it is **conditional compilation**: code wrapped in
`#ifdef DEBUG_TRACE` is included or *entirely deleted* by the
preprocessor depending on a compile-time flag — so the release build
pays zero cost, not even a skipped `if`. That zero-cost property is why
every serious VM ships instrumentation this way.

Runtime errors in a VM need one thing the tree-walker got for free:
**location**. The tree-walker was standing *in* the offending node when
things went wrong; the VM only knows `ip`. But `ip`'s distance into the
chunk identifies the instruction, and (if you keep a side table of
line/offset info, as clox does) that maps back to source. Either way, the
contract is: print a message, stop cleanly, corrupt nothing — no
sanitizer fireworks.

**Why compilers need it:** every production VM has both of these. CPython
can be built with `lltrace` to dump opcodes as they run; the JVM has
whole families of tracing flags. When your `while` loop misbehaves in
task 6.4, the trace will find it in minutes — you're again building the
debugging tool one task before you desperately need it.

**Read first:**
- [Crafting Interpreters ch. 15, §15.1.2](https://craftinginterpreters.com/a-virtual-machine.html) —
  execution tracing (and §15.2.2, stack tracing).
- [Crafting Interpreters ch. 18, "Types of Values"](https://craftinginterpreters.com/types-of-values.html) —
  where clox implements `runtimeError()` with ip-relative location — the
  pattern for your error path.
- [GCC docs — Conditional syntax (#ifdef)](https://gcc.gnu.org/onlinedocs/cpp/Conditional-Syntax.html) —
  the preprocessor reference for the mechanism you're using.

**Done when:** errors print a message and stop cleanly (no sanitizer fireworks);
the trace of `1+2*3` matches your paper prediction.

## Task 6.4 — Globals, print, and jumps in the VM (~1.5–2h)

**Build:** the VM halves of 5.4 and 5.5: a globals table, `OP_PRINT`,
`OP_POP`, and the jump opcodes (`ip += offset` — that's the whole trick).

**The concept:** executing a jump is one line — `ip += offset` (or
`ip -= offset` for `OP_LOOP`) — and that line finishes the story this
project has been telling about control flow. In Phase 4, `while` was a C
`while` re-walking a subtree. Now watch the trace as `OP_JUMP_IF_FALSE`
skips forward over the body when the condition fails, and `OP_LOOP` drags
`ip` backward to the condition again: **there is no loop — only a pointer
that refuses to advance.** The condition's bool, meanwhile, gets popped
and *becomes* control: data turning into flow, which is the whole secret
of computers.

The globals table (names → values, keyed by the pooled name strings from
task 5.4) is your Phase 3 environment reborn on the VM side — same
semantics, new home. Keep the semantics identical to the tree-walker's
on purpose: undefined-variable errors, redefinition policy, all of it.

**Why compilers need it:** after this task, `if`/`while` semantics exist
*twice* in your codebase — tree and bytecode — and the cross-check suite
from 6.2 extends to whole programs: loops, ifs, variables, both back ends
agreeing on every one. Any future semantic disagreement between them is a
bug *somewhere*, found for free. This is exactly how real language teams
regression-test semantics across their interpreter tiers.

**Read first:**
- [Crafting Interpreters ch. 21](https://craftinginterpreters.com/global-variables.html) —
  the VM halves this time (globals).
- [Crafting Interpreters ch. 23](https://craftinginterpreters.com/jumping-back-and-forth.html) —
  the VM halves (jumps).
- [How the CPython VM works](https://tenthousandmeters.com/blog/python-behind-the-scenes-1-how-the-cpython-vm-works/) —
  a guided tour of the real ceval loop; after this task you will read it
  nodding.

**Done when:** the cross-check suite from 6.2 passes on statement programs:
loops, ifs, variables — both back ends agreeing.

## Task 6.5 — Benchmark: tree vs bytecode (~1–1.5h)

**Build:** a tinylang benchmark (a counting loop; fib once functions reach
the VM), timed on both back ends via `clock_gettime`/`clock()` in C or
`time ./build/tinylang ...`. Write the numbers into a `BENCHMARKS.md` with
one paragraph on *why* the gap exists (pointer-chasing vs linear bytes;
cache locality).

**The concept:** the performance gap you're about to measure has a
physical mechanism, and you should be able to narrate it. Memory is slow
and CPUs hide that with **caches** — small, fast copies of recently-used
memory, filled a 64-byte line at a time. Code that touches *adjacent*
bytes keeps hitting lines already in cache; code that chases pointers to
scattered heap addresses keeps missing, and a miss costs on the order of
a hundred cycles of waiting. Your tree-walker is a pointer-chasing
machine: every node visit is a potential miss, plus a recursive C call
with its frame setup. Your VM streams through one contiguous byte array
with everything hot in cache. Same semantics, different memory access
*patterns* — that's the whole gap. This principle is **locality of
reference**, and it's arguably the most practically important fact about
modern hardware.

Benchmarking has its own craft, learnable in miniature here: time the
work, not the startup; run it enough times to see variance; make the
workload big enough that the clock's resolution doesn't lie to you.

**Why compilers need it:** engineering claims need numbers — "bytecode is
faster" is now a measurement *you took*, with a mechanism you can explain
down to the cache line. That combination (measured number + mechanical
explanation) is the difference between folklore and engineering, and it's
your honest capstone review of both execution models.

Where to go next, whenever you want more: call frames for functions in the
VM ([ch. 24, "Calls and Functions"](https://craftinginterpreters.com/calls-and-functions.html)),
strings + a hash table (ch. 19–20), closures (ch. 25), or a garbage
collector (ch. 26) — each is a self-contained expedition from here.

**Read first:**
- [Crafting Interpreters ch. 15, the design note](https://craftinginterpreters.com/a-virtual-machine.html) —
  stack vs register VMs — now you'll actually enjoy it.
- [man page: clock_gettime(3)](https://man7.org/linux/man-pages/man3/clock_gettime.3.html) —
  the timing call, and which clock to ask for (monotonic).
- [Wikipedia — Locality of reference](https://en.wikipedia.org/wiki/Locality_of_reference) —
  the mechanism behind your benchmark's answer.

**Done when:** `BENCHMARKS.md` exists with real numbers from your machine.
