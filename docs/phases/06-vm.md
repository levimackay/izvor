# Phase 6 — The stack-based virtual machine

**Goal:** execute Phase 5's bytecode: a `VM` struct with an instruction
pointer and a value stack, spinning in the classic
`for(;;) { switch(READ_BYTE()) ... }` dispatch loop. End state: the same
tinylang programs run on either back end, and you benchmark them.

**Why:** you are building a CPU in software. The fetch-decode-execute loop
you write here is the same loop inside CPython's `ceval.c`, Lua's `lvm.c`,
and — in silicon — the M-series chip in your Mac. After this phase,
"Python is interpreted" stops being a vibe and becomes a mechanism you have
personally implemented. This is the single strongest talking point this
project gives you.

**Spine reading:**
- [Crafting Interpreters ch. 15, "A Virtual Machine"](https://craftinginterpreters.com/a-virtual-machine.html) — the phase's core chapter.

---

## Task 6.1 — VM skeleton + dispatch loop (~1.5h)

**Build:** `vm.h`/`vm.c`: the VM struct (chunk pointer, instruction pointer
`uint8_t* ip`, fixed-size `Value stack[256]` + stack-top pointer),
`push`/`pop`, and a `run()` loop handling just `OP_CONST` and `OP_RETURN`.

**Why:** meet the two most famous registers in computing, wearing C-variable
costumes: `ip` *is* a program counter, your stack-top *is* a stack pointer.
Making `ip` a raw pointer into the byte array (not an index) is a deliberate,
measurable performance choice — the kind real VM authors argue about.
`ponytail:` fixed 256-slot stack with an overflow check; growable comes if a
real program ever hits it.

**Read first:**
- [Crafting Interpreters ch. 15](https://craftinginterpreters.com/a-virtual-machine.html), §15.1–15.2.

**Done when:** asserts run a hand-built chunk and observe the constant
arrive on the stack; stack overflow is caught, not corrupted.

---

## Task 6.2 — Arithmetic on the stack (~1–1.5h)

**Build:** `OP_ADD/SUB/MUL/DIV/NEG`: pop two, compute, push one. Run real
compiler output for the first time: `compile("(1+2)*3")` → `run` → 9.

**Why:** closing the loop — compiler output meets VM input, and the
post-order insight from 5.3 pays off: it just works, operands are always
where the operator expects them. When it *doesn't* work, you'll learn the
two failure smells of every VM: stack underflow (compiler emitted too few
pushes) and wrong operand order (`SUB` popping backwards: `2-1` giving
`-1`) — the tests target both.

**Read first:**
- [Crafting Interpreters ch. 15](https://craftinginterpreters.com/a-virtual-machine.html), §15.3 (and the binary-op macro trick — your first taste of C macros earning their keep).

**Done when:** a table-driven test asserts `run(compile(src)) == eval(parse(src))`
for a pile of expressions — your two back ends checking each other. That
cross-check is your regression suite for the rest of the project.

---

## Task 6.3 — Runtime errors + a trace mode (~1.5h)

**Build:** graceful runtime errors (div-by-zero, and type errors once bools
flow through), plus a `#ifdef DEBUG_TRACE` mode printing each instruction
(via the Phase 5 disassembler) and the stack contents as it executes.

**Why:** the trace is the VM's flight recorder — every VM has one (CPython:
`lldb` + `dis`; JVM: `-XX:+PrintInterpreter`-adjacent tooling). Watching
`CONST CONST ADD` mutate the stack line by line is also the moment
stack machines go from understood-in-theory to *obvious*. Conditional
compilation (`#ifdef`) is the C idiom for zero-cost debug machinery.

**Read first:**
- [Crafting Interpreters ch. 15](https://craftinginterpreters.com/a-virtual-machine.html), §15.1.1 (execution tracing) and §15.3.1 (runtime errors).

**Done when:** errors print a message and stop cleanly (no sanitizer fireworks);
the trace of `1+2*3` matches your paper prediction.

---

## Task 6.4 — Globals, print, and jumps in the VM (~1.5–2h)

**Build:** the VM halves of 5.4 and 5.5: a globals table, `OP_PRINT`,
`OP_POP`, and the jump opcodes (`ip += offset` — that's the whole trick).

**Why:** watching `OP_JUMP_IF_FALSE` implement `while` by moving `ip`
backward collapses the remaining mystery of control flow: there is no loop,
only a pointer that refuses to advance. After this task your VM runs real
multi-statement programs, and `if`/`while` semantics exist *twice* in your
codebase — tree and bytecode — which is exactly how real language teams
regression-test semantics.

**Read first:**
- [Crafting Interpreters ch. 21](https://craftinginterpreters.com/global-variables.html) and [ch. 23](https://craftinginterpreters.com/jumping-back-and-forth.html) — the VM halves this time.

**Done when:** the cross-check suite from 6.2 passes on statement programs:
loops, ifs, variables — both back ends agreeing.

## Task 6.5 — Benchmark: tree vs bytecode (~1–1.5h)

**Build:** a tinylang benchmark (a counting loop; fib once functions reach
the VM), timed on both back ends via `clock_gettime`/`clock()` in C or
`time ./build/tinylang ...`. Write the numbers into a `BENCHMARKS.md` with
one paragraph on *why* the gap exists (pointer-chasing vs linear bytes;
cache locality).

**Why:** engineering claims need numbers — "bytecode is faster" is now a
measurement you took, with a mechanism you can explain down to the cache
line. This is also your honest capstone review: you understand both
execution models well enough to race them.

Where to go next, whenever you want more: call frames for functions in the
VM ([ch. 24, "Calls and Functions"](https://craftinginterpreters.com/calls-and-functions.html)),
strings + a hash table (ch. 19–20), closures (ch. 25), or a garbage
collector (ch. 26) — each is a self-contained expedition from here.

**Read first:**
- [Crafting Interpreters ch. 15](https://craftinginterpreters.com/a-virtual-machine.html), the design note on stack vs register VMs — now you'll actually enjoy it.

**Done when:** `BENCHMARKS.md` exists with real numbers from your machine.
